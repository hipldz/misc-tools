# 科技短视频口播

目标：让懂一点技术的人，把一件值得讲的事说明白。信息密度来自事实取舍、解释顺序和画面配合；
语气自然来自句子之间确实有话要接。不要靠语气词、夸张评价和密集短句制造人味。

## 适用边界

- 沿用用户已确认的题材、受众、语言、时长和写作偏好。仅写稿且没有其他要求时，可按中文、
  有一定科技常识的普通观众、约两分钟处理，不重新追问已经说过的条件。
- 用户提供参考稿或写作技能时，先读实际内容，借鉴叙述距离、节奏和判断方式。
  缺少参考时继续按本技能写，不声称模仿了未读过的作者，不把一次示例当作固定模板。
- 区分写稿、获取素材、配音和导出视频。只写稿不自动生成 TTS、启动服务或导出 MP4；
  调研、联网和工具操作仍遵守当前任务权限。
- 为本项目制作视频时，同时遵守根目录 `SKILL.md` 与 `docs/agent-skill.md` 的来源和交付约定。
  本技能不增加场景字段、字幕字段或必交的策划文件。

## 先决定什么值得占用口播时间

从给定或经授权核实的原始材料中，挑出具体变化及证据：发生了什么，哪个细节值得解释，
它对谁、在什么条件下有影响。把事实、作者推断、尚待验证的结果分开。
材料不足时删弱结论或指出缺口；不要靠“可能改变行业”把一条薄消息撑长。

每条消息通常只抓一个主要细节。约两分钟的多条新闻可先选两三条，再按重要性分配时长，
无需平均分段；专题或用户指定的条数优先。不要把每条都排成“发布背景—三项功能—意义—提醒”。
不同材料可以从结果、操作、代价或限制切入，也可以直接接着上一条讲。

判断可以鲜明，但要能接上理由。例如，代码合并量暴涨说明工具链承压，并不能直接证明软件质量提高。
没有证据时，不把公司披露写成独立实测，不把演示写成已经可用的产品，不捏造个人使用经历。

## 给声音和画面分工

写稿时在工作笔记中对应每个关键句的依据和画面；默认不把策划表塞进口播交付。

| 声音优先解释 | 画面适合承载 |
| --- | --- |
| 发生了什么变化，为什么会这样，结果或代价是什么 | 原文标题、日期、署名、链接、完整型号和适用范围 |
| 易懂的量级与有意义的前后比较 | 精确数字、单位、坐标轴、测试条件及数据来源 |
| demo 中刚发生的操作和可见结果 | 作者真实 demo、操作位置、前后状态 |

嘴上可以说“三万多次”，原图保留精确值。关键单位和比较口径不能省掉。
改变新闻含义的限制仍要讲出来，例如尚待部署、需要付费或不适用于某类用户；
不能把这些藏进看不清的小字。没有画面的纯音频稿，要把理解必需的信息说完整。

有画面时，解说跟着证据推进，留出看清的时间；不要念一遍截图上的所有字。
缺少实际素材时标为待获取，不编造网页截图、运行结果或“画面里可以看到”的内容。

## 写成一段能接着说下去的话

先写成能一口气讲清的小段，再按自然语义拆字幕。每句话承担一个主要推进：补充事实、解释原因、
给出对比或说明代价。术语出现时，只解释理解眼前这件事所需的部分。

让句子之间有实际关系。例如“手机本地分析聊天”会引出耗电问题，随后才能解释为什么先做轻量筛查。
不要用“接下来”“值得关注”“这意味着”代替中间缺失的解释。直接从有用的事实开头，
结尾可以停在具体结果、尚未解决的问题或一个有依据的判断，不必拔高到整个 AI 行业。

保留自然的长短句变化，合理使用代词和转折。第一、第二人称本身不等于 AI 腔；
是否使用取决于用户的口吻和叙述需要，不用“我用过”“亲测”伪造经历。
不为接近口语硬塞“说实话”“有点离谱”“电池先不答应”“普通人赶紧关注”等句子。
这些表达若确实增加观点，可以保留；如果只是给摘要调味，改成具体内容。

需要参考改法时，读 [references/edits.md](references/edits.md)。例句用于展示取舍，不是换名词就能套用的稿式。

## 压缩和口述复审

按需要在选材、口述和删改之间迭代，不把三个阶段的草稿都交给用户。
逐句检查：

- 删掉这一句，观众会少知道什么？没有实质损失就删，或换成缺少的事实。
- 换一个产品名还能放进别的新闻吗？如果能，检查是否只有通用评价。
- 一遍听下来能否知道主语、数字口径和因果？一句挤了多个意思就拆开，避免碎成口号。
- 判断的理由是否在附近？区分原文结论与自己的解读，语气不要比证据更肯定。
- 观众此时该听解释还是看证据？删去照读画面的部分，为必要的阅读留时间。

时长要给原图、停顿和转场留空间。约两分钟中文可先用五六百字起稿；这是估算，
英语名称、数字读法、声音和停顿都会影响时长。最终以授权生成的真实语音时长为准。
超时先删次要消息、背景和重复判断，不默认通过加快语速压到目标时长。

若没有实际朗读或试听，只报告做过文本层面的口述检查；不能声称“听过很自然”。
自动字数、禁词命中和来源校验都不能证明文风已经合格。

## 交付

单独写稿时，默认只给可直接朗读的连贯正文。来源说明、待核实点和画面建议按用户要求或实际需要另列，
不混进配音正文；不附一大段对自己文风的解释。

为本项目生成完整视频时，把通过复审的口播写入规范的 `narration.segments`，
按完整语义切段，逐句配合实际素材；沿用既有来源说明和交付文件，不另建一套内容协议。
